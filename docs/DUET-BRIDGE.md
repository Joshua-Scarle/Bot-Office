# Claude Duet bridge: design

A two-way message channel between Bot-Office and Claude Duet, the hosted assistant the owner also uses. Goal: high throughput, and low latency from "message sent" to "an agent on the other side is reading it", without either side spending model tokens to check for mail.

## Constraints

- Bot-Office listens on loopback only; the host's only public service is SSH. Nothing may be exposed to the internet, so the other side can never call Bot-Office directly.
- Claude Duet runs in the cloud and cannot reach the host. The one thing that wakes a Duet session from outside is activity on a GitHub pull request it is subscribed to (comments, reviews, checks), delivered as a push event within seconds.
- No secrets in GitHub, ever. The public Bot-Office repo carries only code and this doc.

## Chosen design: a pull request on a private repository as the mailbox

One long-lived draft pull request in a **private** repository (it holds work content, so never this public repo) is the mailbox. Duet to Bot-Office messages are PR conversation comments; Bot-Office to Duet messages are PR reviews (event `COMMENT`). The split matters: a live test showed that plain conversation comments do not wake the subscribed Duet session, while review events do. Duet's own sends are conversation comments, so they do not wake Duet and are read by the controller's poller instead.

| Direction | Send | Wake on the other side | Model tokens while idle |
|---|---|---|---|
| Duet → Bot-Office | Duet posts a PR conversation comment | The controller polls the comment list with a conditional request (`If-None-Match`, about every 4 s). An unchanged list returns `304`, which GitHub does not count against the rate limit. A new message is steered into the target bot's running turn, or starts a turn if the bot is idle. | none |
| Bot-Office → Duet | A bot runs `desk duet send`; the controller posts a PR review (`POST /repos/{repo}/pulls/{pr}/reviews`, `event: COMMENT`) with its own GitHub token | GitHub pushes the review event to the subscribed Duet session, which wakes on it | none |

Message format (first line is a header the other side parses; the rest is the body):

```
[Duet → Bot Office] id=D-20261124-0001 to=<bot name or default> thread=<id> kind=task|question|result|fyi
<body>

[Bot Office → Duet] id=BO-3f9c2a1e from=<bot> to=<main or a Duet channel> thread=<id> reply_to=<id> kind=...
<body>
```

Header values: a value runs up to the next known key (`id=`, `to=`, `thread=`, `kind=`, `reply_to=`) or the end of the line, so `to=Test Bot kind=task` names the bot "Test Bot"; a value can also be quoted (`to="Test Bot"`, straight or curly double quotes; a single quote is a plain character, as in a name like O'Neil). Spaces inside a value are kept (runs of spaces count as one); `thread` and `id` are then reduced to safe characters (a space becomes `_`). `to=` names a bot by its id, its exact name or an alias (when nothing matches exactly: ignoring case and spacing). Only a missing `to=` or `to=default` goes to `default_bot`. A `to=` that matches no bot or more than one, is empty, over 200 characters or has control or invisible characters, has text after its closing quote, or is given twice with different values, or a header with an unclosed quote anywhere, is never guessed: the message is not delivered, the log records it, and Bot Office answers on the mailbox with a `kind=error` review saying why (state `failed`, codes `unknown_bot`, `ambiguous_bot`, `header_unclosed_quote`, `to_too_long`, `to_empty`, `to_invisible_chars`, `to_trailing_text`, `to_conflict`). A notice held back by a send limit stays due (state `undeliverable`, no attempt charged) and is tried again on later polls under a fixed id (`BO-ND-<comment id>`), so it is posted once; any other failure is retried up to 30 times, except a final one (the notice looks like a secret, its earlier outcome is unknown, and similar). This notice may pass the thread cap: the message it answers was admitted under the cap, and each admitted message gets at most one. Outbound, `from_name=` is quoted when the name has spaces (`from_name="Test Bot"`).

A trailing footer block (a `---` line followed by a line starting `_Generated by`) that tools append to a comment is stripped from inbound text.

On delivery the controller adds an "eyes" reaction to the comment as a read receipt and records the times, so `desk duet status` shows send-to-read latency for every message.

## Why this and not something else

- **GitHub webhook to the host:** fastest, but needs a public endpoint on the host. Ruled out.
- **A relay (Cloudflare Worker or similar) with an outbound long-poll from the host:** saves about 2 s on the Bot-Office side, but Duet still can only be woken by GitHub, so it adds a moving part for little gain. Possible later upgrade: GitHub webhook → Worker → host long-poll.
- **The existing poll watcher:** runs a `gh` command every 5 minutes or more with a 60 s debounce. Too slow, and it starts a fresh trigger turn instead of steering.
- **Issue comments (like the old Grok mailbox):** Duet sessions are woken by pull request activity, not issue activity.
- **Email or chat apps:** no push wake into Duet, and slower.

## Expected latency and cost

- Duet → Bot-Office: poll wait (2 s average at a 4 s interval) plus the steer. If the bot is idle, a CLI turn has to start, which dominates (typically 5 to 20 s before the model reads the message).
- Bot-Office → Duet: GitHub's event delivery plus the Duet session waking. Measured in the live test.
- Cost: no model tokens on either side while idle. About 21,600 conditional GitHub requests a day per mailbox, almost all free `304`s. Per message: one GitHub comment or review, one reaction, and the receiving agent's own turn (Bot-Office: the owner's CLI subscription; Duet: one session turn).
- Throughput: a comment or review body holds up to 65,536 characters. The controller caps sends at 40 a minute (GitHub's limit for content creation is about 80 a minute) and keeps per-bot and per-thread caps so two agents cannot loop.

## Safety

- **Private repository only.** Before every outbound post and before any inbound delivery the controller reads `GET /repos/{repo}`: it must say `private: true`, the right name, and the numeric id it had when first seen (pinned in the DB). Polling uses a pass cached for 10 minutes; every delivery batch and every outbound write asks GitHub again first, and a batch stops as soon as any check (also a concurrent send's, and also a network error) fails; that is decided under one lock together with each hand-over. The config is re-read before every hand-over, and a changed or disabled mailbox stops the batch. Any failure (public, renamed, recreated, unreadable) fails closed: nothing is sent or delivered, and status shows the code. A gap of one request remains between that check and the write, so use a token limited to the mailbox repository, and an organization policy that keeps it private, where possible.
- **Authors.** Inbound messages are accepted only from the GitHub accounts in the config, pinned by numeric account id (resolved once from the login, then fixed), of type `User` or `Bot`. Only unedited comments are delivered, so a collaborator who edits an allowed author's comment cannot inject text: the REST timestamps are only a first filter, and right before delivery the controller asks GraphQL for the comment by its node id and delivers only when `lastEditedAt` is null and `includesCreatedEdit` is false, the author's login and numeric id still match, and then uses the GraphQL body. Any error, missing field or mismatch means no delivery (an error is retried, an edit or mismatch is final; status shows the code). The comment text is not stored in the DB. Other comments are ignored and logged by id only, never by content.
- **Fencing.** Inbound text reaches the bot inside `<untrusted-data>` (`rules.untrusted`): any fence marker in the text, in any case or spacing and with lookalike characters, is escaped so it cannot close the block. This holds for both the steer path and the new-turn path (tested). The fence is advisory to the model; what a bot can do with it is still bounded by the usual tool gates and by the send limits below.
- **Outbound.** A job token may send only as `default_bot` or a bot in `senders`; the master token may name any bot. The wire `from=` is the bot's stable id (`from_name=` is the display name). The final serialized review, header fields included, is checked for token patterns, every configured controller credential (any length) and the out-of-repo push denylist on every path (also the bridge's own error notices); a match refuses the send without echoing the value. A denylist named by `BO_PUSH_DENYLIST` that cannot be read refuses the send.
- **Limits and idempotency.** Rate limits and the per-thread cap (canonical thread ids; a message without one inherits the thread it replies to or starts its own) are checked and the send reserved in one SQLite write transaction before the HTTP call. A definite GitHub refusal releases the reservation; a timeout, 5xx or unreadable answer keeps it counted (state `unknown`). A caller-supplied id (`--id`) is never posted twice; ids are scoped to (mailbox, sender), and rows use a random surrogate key. A job token's send is re-checked (job still running, token still valid) under the send lock and again right before the POST. Separately, every outbound attempt is charged before any GitHub request (20 a minute per bot, 60 a minute, 1500 a day) and the charge stays even when GitHub refuses, so rejected sends cannot be repeated without limit. A send that waited for the send lock re-reads the config and re-checks its sender; a changed mailbox refuses it. Inbound messages over the thread cap are not delivered; Duet gets one notice per thread.
- **No lost or replayed messages.** The comment cursor moves only after a complete scan (a page-limit stop keeps it), each poll re-reads a 60 s overlap and comment ids dedupe, and the page-one `304` shortcut is used only when the last scan was one page. An inbound message is recorded as `pending` (with its author's id) before delivery and retried (up to 5 times); pending messages are delivered even when a scan fails, and only while their author is still allowed. Each hand-over writes a receipt keyed by (mailbox, comment id) in its own transaction: the steer message's or the new turn's. A row found `delivering` after a crash is delivered when its receipt exists, else pending again, so a retry cannot duplicate it. Network failures of the edit check use up the 5 attempts; a rate-limit cooldown defers without charging one. Thread lookups, caps, notices and idempotency keys are scoped to the mailbox (and the key to its sender).
- **Shutdown and rate limits.** At most two GitHub requests run at once, and shutdown waits for them. One deadline covers both the wait for a request slot and the request, and the stop flag and cooldown are checked again once the slot is held. Every GitHub request goes through one gate: no request starts after the stop flag is set (a send that cannot start releases its reservation) or during a cooldown that any rate-limited answer set. Each request has a total deadline of 20 s. Shutdown sets the flag on SIGTERM and joins the worker for longer than that before the scheduler stops.
- **Config.** The mailbox repo, pull request number, allowed accounts and senders live in a 0600 config file under the control directory, owned by the controller, in a directory others cannot write, read without following symlinks, never in this repo. `install-config` writes it through an exclusive random temp file and refuses to run inside a bot turn. The GitHub token is described under **GitHub token** below.
- **GitHub token.** The bridge uses the controller's one GitHub token, the file `<control dir>/github-token` (on a default install `data/github-token`; `BOT_OFFICE_GITHUB_TOKEN_FILE` overrides the path), mode 0600, owned by the controller; a symlink or a file others can read is refused. The token is not in this repo, the config, the DB or any log. Today it is a fine-grained personal access token of the owner's account limited to the mailbox repository alone (set up with Pull requests and Issues read/write and Contents read). Like any GitHub token it can also read public repositories, but it cannot write to any other repository (GitHub answers `403`). **It is handed to bots:** it is the same token the controller gives bot runs for GitHub (docs/APPROVALS.md, "GitHub credentials"). Any bot's job (not a job without a bot) gets it for one git or `gh` call at a time, through a one-time ticket (`POST /v1/agent/github-ticket`, then `POST /v1/agent/github-token`), only for a call the controller allows, and each hand-out is logged by operation and repository, never the value. The bot's `gh` gets it as `GH_TOKEN` for that one process and git through `bin/bot-office-credential`; it is not written to the bot's disk or environment otherwise. Effect: a bot holding it can comment on the mailbox pull request as the token's account, which is an allowed author, so such a comment is accepted as an inbound Duet message. The blast radius is the mailbox repository; keep the token limited to it, and if a broader token is ever installed in that file, every bot can use it the same way.
- **Diagnostics.** Status, the DB and logs carry fixed error codes, never exception text or message content.
